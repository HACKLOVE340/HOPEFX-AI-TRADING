# Audit remediation — August 2026

Applied against the external code review of `main@b016566`. This is the handover:
what landed, what was found beyond the audit, what was deliberately not done, and
what still needs a decision from the business rather than an engineer.

Verification for every commit below: `pre-commit run --all-files` clean,
`npm run typecheck` clean, `npm test` 1170 passing, and the backend suites for
api / billing / payments / monetization / auth / settings passing. The 12 backend
failures still present are missing optional ML dependencies in this environment
(`scipy`, `ib_insync`, feed adapters) and fail identically on `main@b016566`.

## 1. Run this before the activation bridge reaches production

```bash
python scripts/backfill_check.py          # or --csv
```

Read-only. It lists customers who completed a payment and never received the tier
they paid for. Until now nothing bridged payment to entitlement, so these
accounts exist unless no crypto payment has ever completed.

**Run it before activation has been live long**, because afterwards a historical
victim is indistinguishable from an ordinary new activation. Keep the output — it
is both the list of people to contact and the record of what happened.

If it returns nothing, check the logs for `DB unavailable — payment` before
concluding nobody was affected: `_save_payment` warned and continued.

## 2. Still off, deliberately

`HOPEFX_PAYWALL_ENABLED` defaults to `false` and should stay there until the
subscription storage question in §5 is answered. Gating reads a module-level dict
that empties on restart; turning the paywall on would 402 every paying customer
after the first deploy.

## 3. Found during remediation, not in the audit

These came out of verifying the audit's claims rather than from the report. Each
is in the commit history with full reasoning.

| What | Why it matters |
|---|---|
| **`POST /api/settings/trading` could clear a risk halt** | Open to any authenticated user, and `kill_switch_enabled` defaults to `False` on its model — so saving *any* trading preference took the "user disabled the kill switch" branch and called `risk_manager.resume_trading()`, whose own docstring says "requires explicit operator action". It also called `kill_switch.deactivate()` with no token, bypassing both the admin gate on `/api/admin/resume` and the `HOPEFX_KILL_SWITCH_TOKEN` requirement — and the resulting exception was swallowed at debug level. |
| **`fmtPnl` dropped the minus sign from every loss** | `value >= 0 ? '+' : ''` combined with `Math.abs()`, so -$500 rendered as "$500.00" in the positions table, portfolio summary and performance page. Used in 15+ places. Found by writing a test for the helper the audit recommended adopting. |
| **Ten more client-supplied identities in `api/monetization.py`** | The audit found `buyer_id` on `/marketplace/purchase` and said to sweep for siblings. There were ten, including `/creators/stripe-account` (point another creator's payouts at your own Stripe account) and `/marketplace/sales` (credit an arbitrary creator an arbitrary amount against a live payout system). |
| **The 2FA QR was generated by a third party** | The audit caught the payment QR going to `api.qrserver.com`; `TwoFactorSetup.tsx` sent the `otpauth` URI to the same service. That URI *is* the TOTP shared secret. |
| **Completing onboarding is what produced the blank wizard** | `finish` wrote the string `'done'` into the step key; the next visit read it back through `parseInt`, got `NaN`, and matched no step. The audit called this an edge case for returning users — it was the normal path. |
| **`Flash` in `FinancialSection` sniffed `/fail\|error/i`** | Same defect as the eighteen colour-sniffing banners, written as a regex, on the panel that resolves chargebacks. The first sweep's grep missed it. |
| **`require_kyc` failed open** | Passes through when no compliance manager is wired. Deliberate for test apps, but this dependency also guards fiat withdrawal, so a mis-wired manager silently disabled identity checks on money leaving the platform. Now fails closed in production. |

### Corrections to the audit

- **The audit's own activation patch would have left renewing customers gated.**
  It set `status = ACTIVE` on an existing subscription without moving
  `end_date`, and `is_active()` checks `start <= now <= end`. A lapsed customer
  would pay and stay locked out. Covered by a regression test.
- **`/trader/:id` has a correct destination already** — `/profile/:id` is
  registered and handles viewing another user.
- **S1 (API-key scopes) is correctly reclassified.** Verified: no `APIKeyHeader`
  or `X-API-Key` dependency exists anywhere in `api/`, `core/` or `auth/`, so
  requesting `admin` grants nothing today. Validation landed anyway — whoever
  builds the verifier would otherwise inherit a table of self-granted claims.

## 4. Not done, and why

**`noUncheckedIndexedAccess` (audit #38).** Enabling it surfaces roughly 150
sites. Each needs a judgement about the correct default, and the tempting fix —
silencing them with `!` or `as` — reintroduces the same crash with the compiler
now asserting it cannot happen. That is worse than the current state, and doing
150 of them at the end of a large change is how it happens.

The concrete crash vectors the audit listed (#39, #40) are fixed, routed through
the existing null-safe formatters. The flag itself belongs in its own reviewable
change. `Portfolio.tsx`'s `!` assertions are sound — each is guarded by a
preceding `length < 2` check — and should be narrowed with a local const rather
than "fixed".

**`PlatformConfiguration.tsx` (175 KB) is still unaudited.** The component is not
declared until line 2321 of 2552; the rest is config schema. Extracting the
schema to a data module makes the remainder reviewable. Not attempted here
because splitting a file that large without being able to exercise it is how you
lose a config field silently.

**Tier-4 hygiene** (emoji → lucide, duplicate shimmer keyframes, blurred orbs,
`100vh` → `100dvh`) is cosmetic and was skipped in favour of correctness. The
mobile `!important` block in `index.css` is load-bearing — retire it page by
page, never in bulk.

## 5. Needs a decision, not an implementation

### 5.1 Which store owns a subscription — the P0

There is no `subscriptions` table. Two stores exist and disagree:

- `User.plan` — a durable, indexed column, read by the superadmin users API.
- `subscription_manager._subscriptions` — a module-level dict with no database
  behind it, read by `require_plan()` and all plan gating.

`monetization/activation.py` now writes **both**, durable first, so a customer
keeps what they paid for even if the in-memory step fails. That is a correct
patch for the payment path and *not* a fix for the architecture.

Two options:

1. **Make `User.plan` the source of truth.** Have `require_plan()` read it
   (cached). Smallest change; the column exists and is indexed.
2. **Add a real `subscriptions` table.** The `Subscription` object already models
   expiry, status, auto-renew and Stripe ids — none of it persisted.

Option 2 is the honest one if trials and renewals are meant to work: `expires_at`
lives only in memory today, so **no trial can actually expire** — a restart
resets the clock and nothing sweeps them.

### 5.2 Flutterwave — keep or drop

Kept and made correct: the charge is derived server-side from the plan, and
verification now grants the subscription instead of returning `verified: true`
and doing nothing. If the answer is "drop it", remove the routes; leaving it
half-wired was the failure mode.

### 5.3 Fiat deposit and withdrawal still persist nothing

`POST /api/payments/deposit` and `/withdraw` generate a reference, return
instructions, and write no record — so `/billing/transactions` never shows them
and no balance moves. The docstrings and log lines now say so explicitly rather
than claiming persistence.

`DECISIONS.md` says the wallet should be a real cash ledger. `wallet_transactions`
exists with `reference`, `status` and `balance_after`, so the table is ready. Two
things must be settled first, and both are money-correctness questions rather
than code questions:

- **`balance_after` needs a row lock.** Two concurrent transactions would
  otherwise read the same prior balance and the ledger diverges. `SELECT … FOR
  UPDATE` on the user's latest row, or a serialisable transaction.
- **Pending withdrawals must reserve funds**, or the same balance is withdrawable
  twice.

Not implemented here: the audit flagged its own draft as written against a grep
rather than a full model read, and a ledger that double-spends is worse than one
that does not exist yet.

### 5.4 Marketplace funding

`purchase_strategy` has a confirmation, an auth gate and the IDOR fix, and
creates a Stripe PaymentIntent. Funding it from the wallet balance instead
depends on §5.3 landing first.

### 5.5 Data export scope

`/settings/privacy/export` returns privacy, integration and accessibility
settings. The Danger Zone button previously promised "audit log, trades, and
account activity" — the copy now matches what the endpoint returns. If the
promise was the intent, extend the endpoint; do not widen the copy back.

## 6. Do not regress these

- **`_resolve_and_validate_webhook_url`** (`api/settings_new_endpoints.py`) looks
  over-engineered. It is DNS-rebinding prevention via IP pinning. Leave it.
- **`api/auth.py` refuses to start rather than silently lose auth endpoints**, and
  enforces the access-token type claim. Its Redis fail-open is a documented,
  deliberate trade-off.
- **Admin routes are uniformly gated** — all `require_role` sites were correct
  before this work. The access-control problems were on the free/paid boundary.
- **The guard tests are the point.** `operator_banner_contract`,
  `sign_display_contract`, `nav_contract` and `symbol_normalisation` exist
  because each of those bugs was copy-pasted into 3–19 places. Deleting a guard
  to make a build pass reopens the whole class.
