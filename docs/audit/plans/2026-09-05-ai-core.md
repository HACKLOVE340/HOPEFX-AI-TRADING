# AI Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use `executing-plans` (or
> subagent-driven development) to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the HOPEFX AI Core — a gateway, guardrails, tool bus, sandbox,
evals gate, cache and operator page — on top of the governance shell the v0
agent already wrote, after first making that shell's gates real.

**Architecture:** `v0/hopefx-remediation` contributed a fail-closed *governance
state machine*: lifecycle contracts, approval/checkpoint/validation ordering,
rate limits and an admin API. It has no engine — no model is ever called, and
its terminal verbs return simulations. This plan keeps the shell (it is good),
repairs five places where it reports success for work that did not happen, then
builds the engine underneath it in dependency order.

**Tech Stack:** Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2.x, pytest;
React 18 + TypeScript + Vite, TanStack Query.

**Spec:** `docs/audit/AI_CORE_SPEC.md` (§2 architecture spine, §3 the nine
concepts, §12 open items). Companion: `docs/audit/TODO.md` items 13–19.

**Source branches:** `claude/add-new-skills-lys862` (this branch, 158 commits of
audit fixes, PR #315) and `origin/v0/hopefx-remediation` (94 commits, branched
from `main@cc7203fe`).

## Global constraints

Every task inherits these. Not negotiable, not restated per task.

* Develop and push only on `claude/add-new-skills-lys862`.
* `ruff check .` clean; `pre-commit run --all-files` clean. Never `--no-verify`.
* Full gate before claiming done:
  `pytest tests/ -m "not slow and not e2e" --cov --cov-config=.coveragerc --cov-fail-under=70 --asyncio-mode=auto --timeout=120 -q`
* Never weaken a risk gate, kill switch, or staleness/drift check.
* Never commit secrets. `prop_firm_mode.json` and `.env.example` hold placeholders only.
* New code goes in `backtesting/`, `strategies/`, `data_layer/` — never the legacy shims.
* Never recreate a top-level `websocket/` package.
* **Every fix ships with a test that fails on the pre-fix tree.** Run it against
  the old code and watch it fail. A test that has never failed proves nothing.
* Compliance-critical paths stay hard-coded (spec §3 concept 9): drawdown limits
  and prop-firm rules are never delegated to a model.

# Part 1 — What the v0 agent actually built

94 commits, 72 files, ~3,200 lines of code (plus a 10,402-line `uv.lock`).
Branched off `main@cc7203fe` (today 13:34), so it is current with main.

## 1.1 What is genuinely good

**`core/ai_contracts.py` (206 lines).** Frozen dataclasses with validation in
`__post_init__` and canonical SHA-256 hashing over sorted JSON. A
`StrategyLifecycle` StrEnum with an explicit `_ALLOWED_TRANSITIONS` table:
research → validated → paper_pending → paper_active → live_pending_approval →
live_approved, with `RETIRED` reachable from every state and terminal. Illegal
transitions raise. `HumanApproval` refuses a live scope without a reason.
`DecisionEvidence` refuses to exist without model version, checksum, feature
schema hash and snapshot time. This is the right shape for an audit trail.

**Gate ordering in `api/safe_agent_platform.py`.** `execute_proposal` requires,
in order: status is `approved_pending_execution` → approval window not expired →
exact confirmation string → a checkpoint exists → a *passed validation in the
selected environment*. Repairs and upgrades require two approvals. That
sequencing is better than most production change-management code.

**Honest self-description in most terminal verbs.** `execute_supervisor_task`
returns `status: "completed_dry_run"` with every tool call marked
`simulated_no_side_effect`; `model_health` returns `"provider_call":
"not_performed"`. Where nothing happens, most of the code says so.

**Secret hygiene.** `_save_state` strips `secret`, `token_value`,
`access_token`, `refresh_token` before persisting integrations. `GET
/integrations` returns `"secret_values": "never_returned"` and means it.

**42 new tests, all passing** — verified in a merged worktree, not asserted.

## 1.2 Eight defects, each proven by execution

Not code-reading opinions. Each was reproduced by running the code.

### D1 · The strategy execution gate is disabled by its own default argument · HIGH

`StrategyExecutionBoundary.evaluate` short-circuits `ExecutionScope.RESEARCH`
to `allowed=True` before any check. Both new call sites default to that scope:

```
dynamic_registry.activate_strategy(self, version_id, scope=ExecutionScope.RESEARCH, approval=None)
strategy_orchestra.activate_ai_strategy(self, strategy_id, scope=ExecutionScope.RESEARCH, approval=None)
```

Every production caller omits the argument:

```
api/dynamic_strategies.py:160   await registry.activate_strategy(request.version_id)
api/dynamic_strategies.py:232   await registry.activate_strategy(latest.version_id)
api/dynamic_strategies.py:242   await registry.activate_strategy(latest.version_id)
api/nocode.py:170               await registry.activate_strategy(version_id)
api/brain.py:301                await registry.activate_strategy(version_id)
```

Measured, with the weakest possible candidate (no validation, no evidence, no
approval):

```
scope=research  allowed=True   code=RESEARCH_ALLOWED
scope=paper     allowed=False  code=VALIDATION_REQUIRED
scope=live      allowed=False  code=VALIDATION_REQUIRED
```

The gate denies paper and live correctly — and nothing ever asks it for paper or
live. Past the boundary, `activate_strategy` sets `version.state =
StrategyState.ACTIVE` and registers it in `self._active`: a real activation, not
a research-scoped one. So the scope argument describes what the caller claims,
not what happens. **This is the audit's signature defect in a new costume: not
"never invoked" but "invoked with a default that makes it a no-op."**

### D2 · The research-evidence gate checks that a string is non-empty · HIGH

`StrategyExecutionBoundary` blocks paper and live unless
`candidate.research_validation_hash.strip()` is truthy, with the reason
"replay, walk-forward, leakage, slippage, and model-quality evidence is
required". `ResearchCandidate.transition()` enforces the same.

But `research_validation_hash` is a plain `str = ""` field that any constructor
may set to anything, and nothing binds it to real evidence. Every occurrence in
the repository:

```
core/ai_contracts.py:142                       research_validation_hash: str = ""      # declaration
core/ai_contracts.py:156                       ... not self.research_validation_hash.strip()
strategies/strategy_execution_boundary.py:44   ... not candidate.research_validation_hash.strip()
tests/unit/test_ai_contracts.py:24             research_validation_hash="research-evidence-sha"
tests/unit/test_strategy_execution_boundary.py:17  research_validation_hash="research-evidence-sha"
```

**Zero production assignments.** The gate is satisfied by the literal string
`"x"`, and the reason code then claims five validations occurred.

Meanwhile the module that computes that evidence —
`ml/research_validation_gate.evaluate_research_validation`, which checks replay,
walk-forward, leakage, slippage costs and model quality — has **no production
importer**. Neither does `ml/model_quality_gate.ModelQualityGate`. Both are
imported only by their own tests. `docs/ai_change_ledger.md` says of the quality
gate: *"Rollback: remove only new gate call sites"* — there are none.

### D3 · `validate_proposal` returns "passed" without validating · HIGH

The status is assigned by an expression over the environment *name*:

```python
"status": "passed" if request.environment in {"sandbox", "paper"} else "blocked_until_paper_passes",
"checks": {"secrets_redacted": True, "live_trading_disabled": True,
           "rollback_checkpoint_planned": True,
           "checkpoint_present": bool(proposal.get("checkpoints")),
           "human_approval_present": proposal["status"] == "approved_pending_execution"},
```

Three of the five "checks" are literals. Nothing is inspected. Measured against
a proposal with `changes={"delete": "everything"}`, no checkpoint and no
approval:

```
validate_proposal(env=sandbox) -> status=passed  checks={... checkpoint_present: False, human_approval_present: False}
validate_proposal(env=paper  ) -> status=passed  checks={... checkpoint_present: False, human_approval_present: False}
```

The two checks that *are* real report `False` and are ignored by the status.
And `execute_proposal` requires "a passed validation in the selected
environment" — which this endpoint always supplies. **This is item 12's defect
(F104, a gate that cannot fail) reproduced inside the AI Core.**

### D4 · `run_diagnostics` claims durable evidence and stores none · MEDIUM

The endpoint builds an `evidence` dict, calls `_save_state(user.sub)` — which
persists only `_PROPOSALS`, `_APPROVALS`, `_INTEGRATIONS`, `_TASKS`, `_ROUTES` —
and returns `"evidence_retention": "persisted_in_audit_store"`. `evidence` is a
dead local. Measured:

```
run_diagnostics returned run_id  : diag-9a04a24cfbde
  claims evidence_retention      : persisted_in_audit_store
  run_id findable in config_store: False
```

The `run_id` handed to the operator refers to nothing retrievable. Separately,
the two "findings" it returns are hardcoded literals, not observations.

### D5 · The approval ledger reports success on a failed write · MEDIUM

`config_store.set` returns `bool` — "True if at least the DB write succeeded" —
and logs `ConfigStore.set: DB write failed` otherwise. `_save_state` calls it
five times and **ignores every return value**. When the DB write fails, state
survives only in module-level Python lists and the endpoint still returns
success to the operator. This fires today: the proof run above emitted
`DB write failed` for all five keys while every endpoint returned 200.

Compounding it: `_PROPOSALS`, `_APPROVALS`, `_TASKS`, `_ROUTES` are module-level
lists mutated in place, loaded once by `_load_state()` **at import time**. Under
more than one uvicorn worker each worker holds a private copy and persists it
wholesale — last writer wins, and approvals recorded in one worker are invisible
to the next. (Same shape as F139: state frozen at import.)

### D6 · Frontend: a scan that fabricates a result, and jams · MEDIUM

`VisionScanner.scan()` in `VisualIntelligenceWorkspaces.tsx`:

```tsx
const scan = async () => {
  setStatus('processing');
  await new Promise((resolve) => window.setTimeout(resolve, 650));
  if (status !== 'processing') return;
  setResult('Visual interpretation is ready for review. Provenance: camera frame, ...');
  setStatus('captured');
};
```

Two bugs in five lines. The result string is fabricated — it sleeps 650 ms and
declares an interpretation ready, having analysed nothing. And it never runs:
`status` is captured by the closure at render time, so after `setStatus('processing')`
the awaited check still reads the old value `'captured'`, `'captured' !== 'processing'`
is true, and the function returns early. The panel jams on "Processing" with a
disabled button, permanently.

Also decorative: the `HologramPanel` "Analyze state" and "Explain decision"
buttons only call local `setState` — no request is made.

### D7 · Every consequential AI action is reachable by any admin · HIGH

All 24 endpoints in `api/safe_agent_platform.py` depend on
`_admin = require_role("admin")`. `_ROLE_RANK` in `api/auth.py` is
`starter 0, user 1, trader 2, admin 3, superadmin 4`, and `require_role` is a
**minimum-rank** check — so rank 3 clears every gate in the module. An admin can
today: approve a proposal, execute it, roll it back, change the model route,
and authorize, revoke or rotate an integration's credentials.

To be fair to v0, one separation-of-duties control **is** correct: an approver
cannot decide twice on the same proposal
(`if any(a["proposal_id"] == ... and a["approver"] == user.sub ...)` → 409), and
repairs and upgrades require two distinct approvers. What is missing is that
both of those approvers may be admins. Nothing requires a superadmin anywhere in
the module, and nothing uses the `require_superadmin_2fa` dependency that
`api/superadmin/_shared.py` already provides for exactly this class of action.

**Consequence:** two admins can together approve and execute an AI-proposed
change without a superadmin ever being involved — which is the "admin overtakes
superadmin" case. Fixed in Task 6b against the matrix in Part 1B.

### D8 · The model settings page saves to nothing, and there is no fallback · HIGH

The owner-facing settings **already exist** — and are inert. `llm_provider`,
`llm_model`, `llm_fallback_provider`, `llm_fallback_model` and
`llm_embedding_model` appear in exactly three places:

```
frontend/src/pages/settings/PlatformConfiguration.tsx   the form (type, default, input)
api/superadmin/_shared.py:458-468                        the PlatformConfigBody fields
api/superadmin/platform.py:251-261                       the defaults dict
```

`GET`/`PATCH /platform/config` round-trips them into the config store. **No

store. So a superadmin can open Platform Configuration, set the primary and
fallback model, save it, and change nothing at all.

**And the fallback does not exist as behaviour, only as a field.** `api/brain.py:653`:

```python
except Exception as exc:
    raise HTTPException(status_code=502, detail="LLM backend error.") from exc
```

One provider failure is a 502. The configured fallback is never attempted,
because nothing reads it and no retry path exists.

**The defaults are also two years stale.** In September 2026 they still read
`llm_model: "gpt-4o"` and `llm_fallback_model: "claude-3-5-sonnet-20241022"`,
both 2024 models; `api/chat.py:183-185` defaults to `claude-sonnet-4-6` and
`gpt-4o`. `config/startup_validator.py:358` restricts `LLM_BACKEND` to
`{anthropic, openai}`, so no third vendor can be selected even by environment.

This is the direct subject of the owner's request, and it is three separate
gaps: the setting is dead, the fallback is absent, and the catalogue is stale.
Fixed in Task 6c (wire the settings), Task 7 (the chain), Task 14 (the surface).

# Part 1A — Model strategy: primary, fallback, and where it is configured

**Owner's requirement (2026-09-05):** the primary model must be a strong hosted
model, *not* one running on our own hardware; local inference stays **optional**;
the choice must be settable in AI settings; and there must be a fallback.

## 1A.1 The governing principle

**Model identifiers are data, never code.** Every chain below is a *default*
written into config, editable by a superadmin at runtime, and overridable per
environment. This is not a style preference — D8 is what happens without it: the
committed defaults still name `gpt-4o` and `claude-3-5-sonnet-20241022`, two
2024 models, in September 2026. Anything hard-coded in a module goes stale
silently and needs a redeploy to fix.

Corollary: the catalogue needs a freshness check, not just good defaults today.
Task 15 adds one.

## 1A.2 Recommended chain, by role

v0 already models routing as a role (`ModelRouteRequest.role` ∈
`reasoning | fast | vision | embedding`). That is the right shape — keep it, and
give each role an ordered chain rather than a single model:

| Role | 1 — primary | 2 — fallback | 3 — second fallback | Local (opt-in) |
|---|---|---|---|---|
| `reasoning` | **Claude Opus 5** (`claude-opus-5`) | **GPT-5.5** | Gemini 3.1 Pro | Ollama |
| `fast` | Claude Sonnet 5 (`claude-sonnet-5`) | Claude Haiku 4.5 (`claude-haiku-4-5-20251001`) | Gemini 3.5 Flash | Ollama |
| `vision` | Gemini 3.5 Flash | Claude Opus 5 | — | — |
| `embedding` | OpenAI `text-embedding-3-large` | Gemini embedding | — | local embedding |

## 1A.3 Why Opus 5 is primary

* It is the latest and most capable model in the Claude family, and the standing
  engineering guidance for building on Claude is to default to the latest and
  most capable model rather than pinning an older one.
* It leads the agentic-coding and agentic-tool-use benchmarks that map onto what
  this system actually asks a model to do — read state, reason over evidence,
  call tools in sequence, and stop when a gate refuses.
* **Lowest hallucination rate of the frontier options.** For a platform that
  reasons about money, a confidently wrong answer is the expensive failure mode,
  not a slow one. This is the property that should decide the primary.

## 1A.4 Why GPT-5.5 is number two — the owner's direct question

Recommendation: **GPT-5.5**, and the reason is not its benchmark score.

1. **It is a different vendor, and that is the whole point of a fallback.** The
   tempting choice is Sonnet 5 — cheaper, faster, same API, one-line change. It
   is also the wrong one: it shares Anthropic's control plane, authentication
   and status page. In the incident a fallback exists for — the primary vendor
   being unreachable — both legs fail together and the fallback is decorative.
   That is the same class of defect as the rest of this document: a control that
   looks present and does not fire. Vendor diversity is the property that makes
   a fallback real; Sonnet 5 belongs in the `fast` chain, not as `reasoning`'s
   second leg.
2. **It is reported strongest at instruction persistence across long agentic
   runs and at multi-step tool orchestration** — precisely the load the MCP tool
   bus (Task 9) places on a model, and precisely where a weaker fallback would
   silently degrade rather than fail loudly.
3. **Honest caveat, and why it is acceptable here.** GPT-5.5's reported
   hallucination rate on AA-Omniscience is high enough that it is called
   unsuitable for compliance-critical output. That would disqualify it if a model
   were ever in a compliance path — and no model ever is, by an existing
   constraint of this plan: spec §3 concept 9 hard-codes drawdown limits and
   prop-firm rules, and the Global Constraints section repeats it. The fallback
   reasons about proposals and evidence; it never computes a risk limit. Under
   that architecture the caveat is contained.

**Third leg: Gemini 3.1 Pro** — a third vendor, so two simultaneous vendor
incidents still leave a working leg; cheapest of the three for this class of
work; and the strongest multimodal option, which serves the camera/vision
surface v0 already built (`VisionScanner`).

## 1A.5 Local inference — optional, never primary

`OLLAMA_BASE_URL` is already wired in `api/brain.py` and stays. Rules:

* Off by default. Never appears in a chain unless a superadmin enables it.
* Never the primary leg for `reasoning`. It may be the **last** leg, or the only
  leg under an explicit `local_only` privacy mode for a deployment that must not
  egress prompts.
* Selecting it must warn in the UI that capability drops sharply, and record
  that acknowledgement in the audit trail.

### 1A.5.1 The local runtime must start with the application — owner requirement, 2026-09-06

**Added after the owner asked for it directly:** the local LLM and any other
local models must come up **at application startup**, so they are running on the
VPS without anyone starting them by hand. Nothing did this. Every part of the
local path assumed an Ollama server that was already listening with the model
already pulled — after a reboot or a fresh deploy, it is neither.

This is worse than a missing convenience, and the reason is `is_credentialed`:

```python
"ollama": ("OLLAMA_BASE_URL",),          # ai/gateway/providers.py
def local_inference_enabled() -> bool:
    return is_credentialed("ollama")     # True because a STRING IS SET
```

Setting an environment variable is not evidence that a server is listening on
the other end of it. So the local leg can sit in a resolved chain, be counted as
available, and answer nothing — a control that reports success for work that did
not happen, which is this audit's signature defect in the AI subsystem itself.

**Requirements, in force:**

1. **Autostart at application startup.** Registered in
   `core/startup_factories.build_component_registry()` like every other
   component, `required=False`, and asserted by a test that reads the registry —
   not by a comment claiming it is wired.
2. **Never blocks or delays startup.** A background task, the same shape as
   `init_hourly_trainer`. The trading engine must not wait on a model download.
3. **Never starts a model the machine cannot hold.** `scripts/vps_capability_report.py`
   already says why: "an oversized model does not degrade, it fails to load or
   swaps the box to a standstill." On a box that also executes orders, swapping
   to a standstill is a trading outage. The runtime measures RAM/VRAM and
   refuses a tier that does not fit, rather than trying and finding out.
4. **Off by default.** Opt-in, so no existing deployment changes behaviour by
   being upgraded.
5. **Failure is never fatal and never silent.** A failure logs at ERROR saying
   what did not start, and leaves the hosted chain untouched.
6. **Readiness is measured, not declared.** Whether the local leg can answer is
   determined by probing the server, never by the presence of an env var.
7. **Models, plural.** The owner asked for "the local LLM and other local
   models" — the runtime takes a list, and warms each one.

### 1A.5.2 Ollama is installed at deploy time — owner requirement, 2026-09-06

**"Make sure ollama is installed when deploying on vps or windows."** The
runtime starts the server and warms the models; it assumed the binary was
already there. Measured on the build machine:

```
ollama     not installed
```

so `_default_launch` raised `OSError("ollama is not installed or not on PATH")`
and the local leg could never answer. Correct fail-safe behaviour, and a dead
end — nothing in `scripts/install.sh` or `scripts/install.ps1` installed it.

| Platform | Path |
|---|---|
| Linux / macOS / WSL | `scripts/install.sh` → `scripts/install_ollama.sh` (skip with `NO_LOCAL_AI=1`) |
| Windows | `scripts/install.ps1` → `scripts/install_ollama.ps1` (skip with `-NoLocalAI`) |
| Docker | `docker compose --profile local-ai up` brings up the `ollama` service |

**The supply-chain decisions, because they are the part worth arguing about:**

* The upstream Linux one-liner is `curl -fsSL https://ollama.com/install.sh | sh`,
  which executes whatever the server returns, unread, as root, on a machine that
  executes trades. The script downloads to a file first, refuses an empty body,
  an HTML error page or anything without a shebang, prints the SHA-256, and
  honours `OLLAMA_INSTALL_SHA256` as a pin that makes an upstream change a
  refusal rather than an execution.
* Windows prefers `winget` — a signed package from the Microsoft repository —
  and the direct-download fallback **verifies the Authenticode signature** and
  refuses anything not validly signed.
* The install is proved by looking for the binary again, never by the installer
  exiting zero. An installer that returns 0 and installs nothing is the
  "success for work that did not happen" shape, and a package manager can
  genuinely produce it.

**`LOCAL_MODEL_AUTO_INSTALL` is off by default.** Installing software is not
something an application does to a trading box on its own; the deploy scripts do
it, where a person is present. When Ollama is absent and auto-install is off,
the runtime refuses with a message naming the script to run — an operator can
act on that, where "not installed" is a dead end.

The compose service sits behind a `local-ai` profile and is not published to the
host: an exposed 11434 is an unauthenticated endpoint that runs whatever prompt
reaches it, on your hardware.

Model *choice* still depends on owner item 2 (the VPS capability report). The
runtime does not need that answer to be built: it reads the tier from
configuration and refuses what does not fit, so it is correct before the report
lands and correct after.


## 1A.6 Fallback semantics — what "fallback" must mean

A chain is only as good as its trigger conditions. Fall through to the next leg
on: connection error, timeout, HTTP 429, HTTP 5xx, and provider-declared
overload. **Never** fall through on: a guardrail rejection (Task 8), a refusal,
a budget denial, or a 4xx that is our own bad request — those are answers, and
retrying them on another vendor just launders a failure into a different one.

Every fall-through emits an audit record naming the leg that failed, the reason
code, and the leg that served the call. A chain that silently degrades is
unobservable, and `python-resilience` (retry with jittered exponential backoff,
per-leg timeout, circuit breaker per provider) is the reference for the
mechanics.

# Part 1B — Authorization model: superadmin vs admin

**Owner's requirement (2026-09-05):** superadmin has access to everything about
the AI; admin is gated so it cannot overtake what superadmin can do.

D7 records the current state: everything sits at `require_role("admin")`, which
rank 3 clears. The matrix below is the target. It reuses what already exists —
`require_role`, and `require_superadmin_2fa` from `api/superadmin/_shared.py`,
which already demands a TOTP-verified token — rather than inventing a new
mechanism.

## 1B.1 The matrix

| Capability | admin | superadmin | 2FA |
|---|:--:|:--:|:--:|
| View overview, agents, model routes, model health | ✅ | ✅ | — |
| View proposals, approvals, tasks, diagnostics, audit | ✅ | ✅ | — |
| Create a supervisor task; plan it; delegate it | ✅ | ✅ | — |
| Run diagnostics (read-only) | ✅ | ✅ | — |
| Create a proposal | ✅ | ✅ | — |
| Request external research (budget-limited) | ✅ | ✅ | — |
| Cancel a task they created | ✅ | ✅ | — |
| Create a checkpoint | ✅ | ✅ | — |
| **Approve a proposal** | ⚠️ one of N | ✅ | — |
| **Execute an approved proposal** | ❌ | ✅ | ✅ |
| **Roll back** | ❌ | ✅ | ✅ |
| **Change a model route or provider** | ❌ | ✅ | ✅ |
| **Change budget ceilings** | ❌ | ✅ | ✅ |
| **Authorize / revoke / rotate an integration** | ❌ | ✅ | ✅ |
| **Enable a tool or change its risk tier** | ❌ | ✅ | ✅ |
| **Promote sandbox → live** | ❌ | ✅ | ✅ |
| **Enable local-only inference mode** | ❌ | ✅ | — |
| View raw prompts in the audit trail | ❌ | ✅ | — |

## 1B.2 The two rules that make it hold

1. **Quorum rule.** A repair or upgrade needs two distinct approvers **and at
   least one must be a superadmin.** v0's existing "an approver cannot decide
   twice" check stays and is correct; this is added on top of it. Without this,
   two admins alone can approve, which is the overtake case.
2. **Execution rule.** Approval and execution are different privileges. An admin
   may contribute an approval; only a superadmin may execute, roll back, or
   touch credentials, models, budgets or tool risk tiers — and those need
   `require_superadmin_2fa`, not merely the superadmin role, because a stolen
   token should not reach them.

## 1B.3 STRIDE notes (elevation of privilege)

* **Rank inflation.** `require_role` is a minimum-rank check, so any future role
  ranked above `admin` silently inherits admin's AI powers. Task 6b's test
  asserts the *exact* set of roles admitted by each endpoint, not just that
  admin is admitted.
* **Confused deputy.** An admin who cannot execute may still create a proposal
  whose `changes` payload, once executed by a superadmin, does something the
  admin could not do directly. Mitigation: the execute path re-validates the
  proposal against the *executing* user's rights, and the approval UI renders the
  full diff of `changes` — never a summary.
* **Repudiation.** Every allow and every deny records actor, role, endpoint,
  reason code and evidence hash. A denial that leaves no trace cannot be
  distinguished from an attempt that never happened.
* **Information disclosure.** Raw prompts can carry secrets and position data.
  Admins see prompt *hashes* and metadata; only superadmin sees raw text. v0's
  existing secret-stripping in `_save_state` stays and is the precedent.

## What Task 7 left open, and how it closed

The gateway shipped complete except for the one thing that made it load-bearing:

built around a `Provider` protocol that only tests implemented, while

`security/self_healer.py` called Anthropic, OpenAI and Ollama inline.

That is not a partial task — it is the audit's signature defect, a control that
is real and bypassed, reproduced by the fix for it. Closed in `71b58560`:

four callers were migrated, and `tests/unit/test_no_model_call_bypasses_the_gateway.py`
asserts the boundary from the AST rather than by convention.
