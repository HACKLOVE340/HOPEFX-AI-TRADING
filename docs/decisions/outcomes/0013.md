# Outcome 0013 — `data/` owns streaming and serving; `data_layer/` owns access

- Decision: 0013
- Status: observed
- Observed: 2026-09-13

## Expected

"Which package does this belong in?" becomes answerable, closing the defect class
F216 named, at a cost of "one paragraph in CLAUDE.md and nothing else". Three
packages where a reader might expect one, so the rule must stay visible in the
routing table "or it will be re-litigated". And explicitly: *does not authorise
moving existing code between them.*

## Actual outcome

Adopted as a rule and honoured as one. The paragraph is in `CLAUDE.md`, with the
per-package table and the boundary stated in ADR terms. Measured 2026-09-13,
production importers (tests, scripts and the virtualenv excluded): `data_layer/`
80, `data/` 18, `market_data/` 8 — the same shape as when the decision was taken.

No module has been moved across the line. That is the decision working, not the
decision being ignored: it was explicitly a description of what the code already
does, and the importer count was named as the cost of pretending otherwise.

The re-litigation risk has not materialised in four days, which is not yet
evidence either way.

## Lessons

The most useful sentence in the record is the one that withholds permission:
*"Does not authorise moving existing code between them."* A boundary rule with no
such sentence reads as a refactor mandate, and a well-intentioned contributor
tidying 18 modules across a line that 106 call sites depend on would have cost
far more than the confusion it fixed.

The record before it was also right to refuse. `CLAUDE.md` previously said the
boundary was documented nowhere and that it would not invent one — correct at the
time, since inventing a convention without the owner is how a guess becomes law —
and it left the defect class live for as long as that lasted. The lesson is that
"decline to decide" is a legitimate position with a running cost, and the cost
should be named when the position is taken.
