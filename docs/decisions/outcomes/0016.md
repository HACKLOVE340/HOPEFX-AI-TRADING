# Outcome 0016 — Root documents are authoritative; ARCHITECTURE is re-subjected

- Decision: 0016
- Status: observed
- Observed: 2026-09-13

## Expected

*"Takes the registry's contested-subject count from 3 to 0 and closes Group 3
item 8."* `CONTRIBUTING.md` and `DEPLOYMENT.md` at the root become authoritative
with the `docs/` copies marked `superseded`; `ARCHITECTURE.md` takes the subject
`architecture_module_map`, because it and `docs/architecture.md` are two
documents with two subjects, one of them mislabelled.

## Actual outcome

**It was 3, four days after the record said it would be 0. It is 0 now, and
applying it was the ledger's first paid-down finding.**

Measured on 2026-09-13 with `python scripts/docs_registry.py --check`, *before*
this entry was written:

```
note  [duplicate_subject] subject 'architecture'   claimed by ARCHITECTURE.md, docs/architecture.md
note  [duplicate_subject] subject 'contributing'   claimed by CONTRIBUTING.md, docs/CONTRIBUTING.md
note  [duplicate_subject] subject 'deployment'     claimed by DEPLOYMENT.md, docs/DEPLOYMENT.md
```

`docs/REGISTRY.toml:33` still read `subject = "architecture"` for
`ARCHITECTURE.md`, and neither `docs/` copy had been marked `superseded`. The
reasoning in the record was sound and nobody had disputed it; the edit simply
never happened, `--check` classified the three as `note` / baselined, so nothing
failed and nothing said so.

Applied the same day, exactly as the record specifies and nothing more:

* `ARCHITECTURE.md` → `subject = "architecture_module_map"`
* `docs/CONTRIBUTING.md` → `state = "superseded"`, `superseded_by = "CONTRIBUTING.md"`
* `docs/DEPLOYMENT.md` → `state = "superseded"`, `superseded_by = "DEPLOYMENT.md"`
* `known_duplicate_subjects` → `[]`

Neither `docs/` copy was deleted — the owner's standing instruction is that
nothing is removed, and the record says subordinate, not gone. `--check` now
reports **0 contested subjects, 0 blocking**, and
`tests/unit/test_docs_registry.py::TestTheLiveRegistryIsHonest` asserts it
against the live registry rather than against the baseline, so the count cannot
quietly climb back. That test is red on the pre-fix registry.

## Lessons

The gap between intent and reality was **one command away the whole time** — the
outcome was already a number, "3 to 0", computed by a script that runs in
`pre-commit`. Nobody ran it against the record, because nothing connected the
two. That connection is what this ledger entry is, and it is the argument for
writing `## Expected` as something a reader can go and test rather than as a
paraphrase.

The second lesson is about `note` as a severity. Three baselined notes were
indistinguishable from three notes a decision had promised to remove. **A
baseline that outlives its debt hides the next one**, so clearing the baseline is
part of paying the debt, not paperwork after it — the paydown here removed the
three subjects from `known_duplicate_subjects` in the same change.

Clearing it also broke the pre-existing test that asserted every baselined
collision is still reported: with an empty baseline its central assertion is
vacuous, and a scan that matched nothing agrees with every conclusion (F255).
It now injects a synthetic collision to prove the detector is live before
concluding from silence. A test written to track debt should say in advance what
it will assert once the debt is zero, or it punishes the paydown it exists to
encourage — the same trap its own comment records escaping once before, when the
`api` collision was fixed.
