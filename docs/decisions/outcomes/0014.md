# Outcome 0014 — Run the `slow` and `e2e` tiers nightly, not per-PR

- Decision: 0014
- Status: observed
- Observed: 2026-09-13

## Expected

"Makes the 209 real: integration drift is caught within a day instead of never."
Per-PR feedback stays fast. A new failure mode to design for was named in
advance: *"a nightly that fails and is ignored is the same dead control in a
different costume."*

## Actual outcome

**The nightly does not exist.** Measured 2026-09-13, four days after the record:

* No workflow in `.github/workflows/` runs `pytest -m "slow or e2e"` on any
  schedule. `tests.yml:125` and `ci.yml:421` both pass `-m "not slow and not
  e2e"`, and neither has a `schedule:` trigger at all.
* The only nightly `cron` in the repository is `load-test.yml` (03:00 UTC), which
  runs a load test, not the test tiers.
* `ci.yml:621` has a job named `e2e`, and it is Playwright against the frontend —
  a different thing that happens to share the word.
* The tier is real and has grown: `pytest -m "slow or e2e" --collect-only`
  collects **210 tests**.

So 210 tests are deselected everywhere and selected nowhere. They run when a
person runs them.

The predicted failure mode was "a nightly that fails and is ignored". The actual
one is a step earlier and worse, because there is no red build to ignore —
nothing reports anything, so the absence generates no signal whatsoever.

## Lessons

This is the ledger earning its keep on its first pass, and it is uncomfortable:
the decision was recorded, accepted, cited, and never built. Nothing in the
registry could have surfaced that, because a registry records intent. Four days
of believing the 209 were covered is cheap; four months would not have been.

The general shape is `hopefx-dead-controls` applied to process rather than code —
*a control that exists, is documented accurately, and never runs.* Here the
control is a CI schedule and the documentation is an accepted ADR, which is about
as authoritative as documentation gets in this repository.

**Follow-up, and it belongs to this decision rather than a new one:** either add
the scheduled workflow, or supersede 0014 with a record that says the tiers run
on demand and why. What must not happen is the record continuing to assert a
nightly that no file implements. Note that the branch's CI does not execute at
all today (finding F95 — no runner is assigned), so adding the workflow closes
the gap in the repository while leaving it open in practice until that is
resolved; both halves need saying when it is.
