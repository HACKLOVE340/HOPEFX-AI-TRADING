# Outcome 0010 — Where the decision ledger lives, and why it is not a second audit log

- Decision: 0010
- Status: observed
- Observed: 2026-09-13

## Expected

"What did the platform decide, and what did it refuse" becomes a single query,
and `ai/core/calibration.py` finally gets the `resolve()` caller it was built for
and never had. The named failure mode: *"If a later change has the ledger keeping
its own tier list or its own calibration, this decision has been undone in
substance while the file still exists."*

## Actual outcome

Built and still shaped as decided. `ai/ledger/` holds `decisions.py` (Chapter 7)
and `outcomes.py` (Chapter 8). `ai/core/calibration.py:98` defines
`resolve(agent, *, key, correct)` and it now has a caller, so a stated confidence
is scored rather than merely stated.

The substantive-undoing check was run explicitly for this entry rather than
assumed: the ledger still imports the tier list rather than restating one, and
still delegates calibration. Entries remain frozen, with an outcome attached by
replacement.

Refusals are first-class entries, which is the part that makes the single query
worth having — a system that logs only what it did cannot tell you what it
declined to do.

## Lessons

This record did something unusual and worth copying: it wrote down **what its own
reversal would look like** — a second tier list, a second calibration — so the
reversal is checkable rather than arguable. Most records name consequences; this
one named the evidence that would prove it had been abandoned. That turned
verifying it from a judgement call into a grep.

The distinction it drew from `scripts/adr.py` also held up: one option is
legitimate for an automated router and forbidden for an ADR, and a prediction is
required here and not there. Two record systems with deliberately different rules
did not converge or collide.
