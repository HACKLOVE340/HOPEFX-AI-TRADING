# Outcome 0001 — Pin Python to 3.12

- Decision: 0001
- Status: observed
- Observed: 2026-09-13

## Expected

Artifact loading becomes predictable and the Dockerfile becomes the single source
of the version. The coupled-change hazard was named in advance: altering the
Dockerfile's Python without altering the retrain workflows in the same commit
reintroduces the defect.

## Actual outcome

The pin holds everywhere it was supposed to. Measured 2026-09-13:
`Dockerfile:35` is `python:3.12-slim`; `ci.yml`'s test matrix is
`["3.11", "3.12"]`; both `retrain.yml` and `quarterly_retrain.yml` run 3.12 at
every setup step, so `.pkl` artifacts are pickled on an interpreter production
loads them on.

The interesting half is what the decision was reacting to. `CLAUDE.md` had
asserted 3.10 "matches the Docker image", and that was false in both directions
at once — the image was already 3.12, and 3.10 was tested by nothing. Anyone
following the documented guidance produced artifacts under an interpreter neither
CI nor production ever loaded. The record fixed the statement; the code had never
been wrong.

## Lessons

The defect was in the document, not the build, and the document was the thing
people acted on. A version pin is only as good as the sentence that explains it,
because the sentence is what a contributor reads before reaching for a
`python_requires`.

The coupled-change hazard the record predicted has not fired — but nothing
enforces it either. There is no check that the Dockerfile's Python and the
retrain workflows' Python agree; today they do because a person kept them
agreeing. That is a candidate for a gate, and it is worth noting that the record
identified the risk correctly and stopped at naming it.
