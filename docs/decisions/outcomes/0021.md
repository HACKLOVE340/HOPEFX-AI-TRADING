# Outcome 0021 — The fiat wallet is the ledger the money path writes through

- Decision: 0021
- Status: pending
- Review by: 2026-12-17

## Expected

`wallet_transactions` starts being written, so AML's daily withdrawal **count**
and **volume** rules fire for the first time and `health_check_service.py`
aggregates something other than zero. Every money movement gains an
exact-`Decimal` audit row whose reconciliation check refuses rather than drifts.

The credit side must land before the debit side, because a debit against an
empty wallet refuses with "Wallet not found" or "Insufficient subscription
balance". The credit path needs a database uniqueness constraint, not a
read-then-write check, because Stripe delivers webhooks at least once and a
replayed `payment_intent.succeeded` that credits twice creates capital out of
nothing.

Money is *recorded*, not *disbursed*. `FIAT_PROVIDER` stays unconfigured.

## Actual outcome

`pending` on the decision's own terms — the ledger is wired end to end, but the
debit half is shipped OFF, so production has not yet exercised it.

**Both tasks are built and proven.** Deposits credit on
`payment_intent.succeeded`; withdrawals debit behind `WITHDRAWAL_DEBITS_LEDGER`.
Both P0s closed on their own probes' measurements rather than on a claim:
`WALLET-DEAD` OWNER → FIXED ("the wallet ledger has 1 production consumer(s)"),
`AML-UNREACHED` PARTIAL → FIXED.

**What actually came alive in AML, measured by executing it.** Rule 5 (rapid
turnaround — a withdrawal within N hours of a same-amount deposit, a layering
pattern) reads `transaction_type == "deposit"` and now has rows. Rule 3 (daily
withdrawal count) is proven to fire: six same-day withdrawals against a funded
wallet, the sixth refused with 403 by compliance rather than 402 by the balance
check. That rule had never had a row to count in the history of this codebase.

**Where the expectation did not hold.** The Expected section says the credit
path "needs a database uniqueness constraint, not a read-then-write check". It
got both, and the split was then measured rather than assumed: with the Python
check disabled a replay STILL writes one row, because
`uq_wallet_txn_user_reference` refuses the insert and `_apply_movement` rolls
back. The database is the guarantee. The Python check only buys an honest log
line — without it a routine Stripe retry reports "Ledger write failed" with an
IntegrityError traceback at ERROR, which reads like a broken ledger.

**What the decision did not anticipate at all**, and the reason the debit ships
dark: `api/billing.py::get_balance` promises "the authenticated user's wallet
balance" and reads the BROKER account. The number a user sees and the number a
withdrawal is refused against come from different sources, and the ledger has no
history. Unflagged, every withdrawal would refuse 402 for users the UI says have
funds. Recorded as `BALANCE-SOURCE-SPLIT` (P1, OPEN) rather than papered over.

## Lessons

One, already, and it is the reason this record is not empty: **the obvious fix
was the wrong one, and it would have looked right.** `WALLET-DEAD`'s own
test-first note says to drive a withdrawal through the API and assert a row
lands in the ledger. Wiring `POST /payments/withdraw` through `debit_wallet` —
the one-line change the finding invites — would have given the register the
production caller it measures for, while making every withdrawal fail, writing
no row, and leaving AML's daily rules exactly as unfireable as before. The
finding would have read FIXED and nothing would have been.

It was caught by reading `_apply_movement` rather than the method name: it
auto-creates a wallet on credit and refuses on debit. That asymmetry is the
whole reason the task order is credit-then-debit.

Second, smaller: the identity gap was not in the register at all. It was found
while planning, by asking what the webhook would actually have to know. A
finding that names a fix does not always name its prerequisites.

Third, and it generalises: **reading the code found three defects that building
it would have found later and more expensively.** The refusal mapping was four
cases and should have been eight — collapsing them would have hidden a
balance-did-not-reconcile corruption behind a 402. `debit_wallet` fails closed
unconditionally while the endpoint's screen passes through in development, so
wiring them together would have refused every local and test withdrawal, and
`_screen_withdrawal_for_aml`'s own docstring predicts what happens next: "that
is how a gate gets disabled by whoever is trying to work." And `get_balance`
reads a different number than the one the debit checks. None of the three was in
the register. All three came from a read-only pass taken while a suite ran,
which cost nothing.
